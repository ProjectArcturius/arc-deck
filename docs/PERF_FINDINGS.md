# Saiku Deck · 流式排版性能实测

> 探针：`probes/layout-bench`。全部数字为 **release** 构建、单机实测（Windows，
> 字体 `simhei.ttf` 9.3 MB，字号 15.0）。复现：`cargo run -p layout-bench --release`。

## 为什么测这个

Agent GUI 的性能瓶颈**不是绘制，是文本排版**。流式追加时每个 token 都改变消息
内容，而排版缓存的键是**内容派生**的 —— 于是可能整条消息每来一个 token 就要
重新塑形/换行/光栅化。一条两万字的助手回复，若每次追加都全量重排，这就是天花板。

这个数字必须**在写渲染管线之前**拿到，否则管线定型后返工。

## 实测结果

| 规模 | 断行 UAX#14 | 塑形 rustybuzz | 光栅化 fontdue（冷启动全量） |
|---|---:|---:|---:|
| 2,085 字符 / 15 行 | 0.015 ms | 0.419 ms | 3.809 ms |
| **20,016 字符 / 144 行** | **0.142 ms** | **4.313 ms** | **32.192 ms** |

字体解析（`fontdue::Font::from_bytes`，9.3 MB）：**563.4 ms** —— 只做一次，常驻。
`rustybuzz::Face::from_slice`：< 0.1 ms（惰性，不解析字形轮廓）。

单个字形光栅化均摊：**0.0017 ms**。

## 判读（数字说明了什么）

### 1 · 光栅化是最大单项，但它**可缓存**

32.2 ms / 18,432 字形。而单字形均摊仅 0.0017 ms —— 差距全在「首次」上。

**稳态下每个 token 只引入 0-1 个新字形**，因此只要按 `(字符, 字号)` 键做字形缓存，
光栅化成本就降到一次查表，**与消息长度无关**。

> 结论：必须尽早引入字形缓存。这不是优化，是前置条件。
>
> 好消息：上游 `kanesumi-canvas` 的 harness 侧已有「R8 字形纹理 + 内容去重」的
> 实现参考。

### 2 · 塑形成本随长度线性，但**上游已有按行缓存**

4.3 ms / 20,016 字形是**冷启动全量**数字。而上游 `text.rs` 的缓存是**两级**的：

| 缓存 | 键 | 流式追加时的行为 |
|---|---|---|
| `ShapeKey`（L208、L334 `shape_line`） | **按行**（行文本 + 字号 + 字距） | **已确定的行命中，不必重新塑形** ✓ |
| `LayoutKey`（L218） | **按整段** `layout_box` 调用 | **整段未命中，换行全量重算** ✗ |

**所以真实瓶颈不是塑形，是「按整段的 `layout_cache`」。**

每次追加的代价 = 一次整段换行 + 一次整段逐行测量；只有新出现的尾行需要塑形。

> 我最初的判读说「塑形需按段落增量」—— 那条**不准确**，上游已经做到了按行缓存。
> 真正要动的是 `LayoutKey` 的粒度。

### 3 · 换行必然全量，除非在段落级切分

关键机制：**当一行溢出时，其内容会在前置文本边界处【换行】，而后置文本可能
级联换行** —— 因此换行**不能**局部缓存，除非按段落切分。

> 早先版本从**末尾**截断 token 做缓存，结果**超长段落**产生了一个坏情况
> （这正是「按整段 layout_box 缓存」这个设计的由来）。

这条注释是整份材料里最有价值的一句：它说明上游已经踩过一次坑，并把结论
固化成了设计。

### 4 · 为什么这个风险是「有条件的」而非全局

上游注释确认：缓存的优化目标是**静态文本**（时钟 / 应用名 / 菜单项）。
稳态下长转录是静态的 —— 只有正在流式的那一条在变。

**所以真正的最坏情况是「一条很长的消息 + 正在流式追加」**，而不是整个会话。

## 结论与后续设计约束

| 设计约束 | 依据 |
|---|---|
| **必须**做字形缓存，键 `(字符, 字号)` | 光栅化 32 ms 全在「首次」，稳态可降到查表 |
| **必须**让流式文本按**段落/块**切分后再进 `layout_cache` | `LayoutKey` 按整段，长段落是坏情况；上游注释明说踩过这个坑 |
| 塑形可依赖上游按行缓存，**但需确认** `ShapeKey` 在追加场景下的命中率 | `shape_cache` 按行，理论命中率高，实测待做 |
| 字体解析 563 ms 必须**只做一次**并常驻 | 否则每次重排都会付这个代价 |
| 单段落超长（数万字无空行）是需专门处理的坏情况 | 换行级联不可局部缓存 |

**优化方向明确**：字形缓存 + 段落级布局切分。二者都不需要改动上游的塑形层。
